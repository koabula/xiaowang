# 第三批优化与对比

2026-11-17，macOS arm64，Node v26.13.1。读取优化：`b1204cc`；下载优化：`cedac86`。原始结果见 [performance-batch3.json](performance-batch3.json)。

## 实施范围

- 侧栏摘要使用索引从最新消息开始读取，保留原来的空白、附件和摘要规则。
- 任务补充为空时直接返回；有补充时只查当前 Bot 对应的事件编号。
- PDF 进入现有解析缓存前不再整文件读取。其他扩展名只读 5 字节判断是否为 PDF，兼容扩展名错误的资料。
- 保持既有 80 MiB 资料上限。PDF 抓取检查未压缩响应的长度，并按接收字节数限制正文；超限或控制权切换时终止请求，继续使用原浏览器登录会话。
- 原生下载检查声明大小、进度和最终文件大小。每次下载拥有独立临时目录，在完成、取消、中断、导入失败及正常退出时清理。导入只接受完整且未超限的文件。

UI、交互和配置项没有变化。没有引入新的缓存层、队列或依赖。

## 同一数据的读取对比

基线源码为 `0bcac33`，优化版使用同一个数据库和 PDF 文件。10 个 Bot、10,000 条历史事件，加任务及补充事件共 10,008 条；PDF 为 40 页、约 8 MiB。同步读取预热 5 次，取 31 次中位数；PDF 先完成首次解析，再连续读取 40 页并取中位数。

| 路径 | 优化前 | 优化后 | 实际读取量变化 |
| --- | ---: | ---: | --- |
| 10 个侧栏摘要 | 13.268 ms | 0.632 ms | 10,008 → 10 条事件 |
| 无补充的任务 | 1.128 ms | 0.001 ms | 1,008 → 0 条事件 |
| 两条补充的任务 | 1.187 ms | 0.033 ms | 1,008 → 2 条事件 |
| PDF 缓存后的按页阅读 | 0.791 ms | 0.016 ms | 主线程整文件读取 40 → 0 次，约 320 MiB → 0 |

侧栏摘要与原算法逐项一致。两次 PDF 输入 SHA-256 均为 `5e56ad4b37c836ce65d5282227319762a5b2a333a71769a8df3643cd8d295c73`，40 次阅读输出 SHA-256 均为 `411010edb07b8462270464b9155593a162f35f78f6062e11c4460b35e356b059`。

这些耗时是本机数据路径的测量，不代表完整页面刷新时间。PDF 首次解析仍需读取原件；这里消除的是后续缓存命中时多余的主线程整文件读取。

## 同一数据的下载对比

`benchmark-downloads.mjs` 分别给旧版完整缓冲算法和新版受限读取算法提供完全相同的 96 MiB 正文，内容均为字节 65，每块 1 MiB；上限保持 80 MiB。

| 响应 | 旧算法读取正文 | 新算法读取正文 | 新算法行为 |
| --- | ---: | ---: | --- |
| 已声明 96 MiB | 96 MiB | 0 | 读正文前拒绝并取消 |
| 没有声明长度 | 96 MiB | 81 MiB | 第一块超过上限时拒绝并取消 |

这是固定数据流对比，不是公网速度测试。未知长度需要接收跨过上限的那一块才能确认超限；真实网络还可能存在传输缓冲。已接受的文件仍会在上限内组装为 Buffer，未改变资料库接口。压缩响应按解码后正文大小检查，避免把压缩包长度与文件长度混淆。

## 复现

```sh
node scripts/benchmark-reads.mjs /tmp/xiaowang-batch3-fixture > /tmp/reads-after.json
node scripts/benchmark-downloads.mjs > /tmp/downloads.json
```

读取脚本会首次生成并保存固定资料，后续复用同一路径。复现旧版时，在单独目录提取 `0bcac33` 的 `src/`，复制当前 `benchmark-reads.mjs` 和 `package.json`，复用相同依赖；先运行旧版，再运行新版，两次均传入同一个资料目录。脚本自动选择旧版或新版查询路径，并验证输出一致性。
