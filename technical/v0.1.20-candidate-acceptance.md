# v0.1.20 候选包隔离验收

日期：2026-11-17。分支：`codex/v0120-isolated-acceptance`。

## 范围与隔离

安装、实际自动更新、重启和数据保留均在 GitHub Actions 的一次性 macOS arm64、macOS Intel、Windows x64 和 Linux x64 机器运行。安装脚本拒绝在普通本机环境运行。使用真实安装包和原始 SHA-256 清单，不解包修改应用代码，也不把本机账号密钥上传至 CI。

本机仅运行隐藏窗口的回归测试，禁止显示、获取焦点及访问系统剪贴板。真实服务测试脚本也改用相同的后台启动方式，支持连接发行应用。

自动更新验收使用原始 v0.1.19 发行安装包，以本地更新源提供未经改动的 v0.1.20 候选包。模拟模型只用于产生可核对的固定任务记录，不用于声称真实模型或语音效果通过。

## 发现及必要修复

原始候选构建：[44005768651](https://github.com/koabula/xiaowang/actions/runs/44005768651)，提交 `6117667`。

- macOS 两种架构均通过全流程，Linux AppImage 也通过安装、真实自动更新和数据保留。
- Windows 新安装首启时，Chromium 把路径 `RUNNER%7E1` 显示成 `RUNNER~1`，应用按 URL 原始字符串比较，误拒绝自己的 IPC 请求。提交 `4fbe50b` 改为比较 `fileURLToPath` 解析后的文件路径；仍要求同一协议、主机和应用文件，HTTP 开发页面继续精确匹配。增加编码差异及错误页面回归检查，后台权限边界测试通过。UI、交互、设置和正常启动行为未改变。
- Linux DEB 最初直接用 `dpkg` 安装，隔离机器缺少安装包已声明的 `libnotify4` 依赖。改用 `apt-get` 解析依赖，属于验收环境修正；不修改产品依赖。失败报告提前落盘，修正测试服务的关闭顺序，便于失败后正常退出。
- 安装器后代进程继承了原应用的输出管道，产品检查全部通过后测试仍不能退出。关闭候选应用时释放这些测试管道后，Linux 验收正常完成。Windows 重启进程的系统路径为长路径，脚本原先用短路径查找；改用规范路径后完整复验通过。这两项只修正验收工具。

按后续产品要求，提交 `953a962` 只在前端隐藏设置中的千问入口：保留协议实现与旧资料，旧用户打开设置不会自动改写原服务，也不会串用其密钥。提交 `9956cd1` 在中英文 README 加入“目前测试中，豆包的用户体验最好”，并同步可选服务列表。

最终候选构建：[44012739335](https://github.com/koabula/xiaowang/actions/runs/44012739335)，产品提交 `9956cd172ece4702faa9692100b61a48842ddb56`；包含 Windows 首启修复及上述前端和文档修改，三平台构建全部成功。此后提交只修改验收工具与记录，无需重建产品包。

## 数据保留的判断标准

通过旧版公开接口创建一个 bot，保存文字和语音测试密钥，导入固定 PDF 并完成一次任务，写入带 `xwref` 的笔记，然后实际触发应用更新：

- 新安装的干净用户目录可进入设置页，版本正确。
- 更新后版本正确，设置就绪，两个密钥的提示和原模型设置保留。
- 活跃 bot、任务 ID、完成状态和执行次数保留；模型总请求数仍为一次，已完成任务没有重跑。
- 展示事件完整一致，资料 ID 一致，笔记文件哈希一致。
- 更新后打开原笔记，点击原引用，PDF 原文正常显示。
- macOS 和 DEB 直接连接自动重启后的应用检查；Windows 和 AppImage 先确认更新器确实自动拉起新进程，再关闭它并以同一安装位置和默认用户目录重开检查数据。

## macOS 钥匙串提示的范围

用户提供的 v0.1.19 截图是系统请求访问 `xiaowang Safe Storage`。该版本用 Electron `safeStorage` 加密本地 `secrets.bin`，读取设置时从钥匙串取得应用的解密密钥。拒绝后当前实现返回空设置，原文件不会仅因拒绝而删除。

发行配置在未提供开发者证书时使用 ad-hoc 签名。[Electron 官方说明](https://www.electronjs.org/docs/latest/api/safe-storage#platform-specific-key-providers)指出，缺少有效且一致的签名可能导致更新后重复请求钥匙串授权。首次解密需要系统授权有明确用途；重复授权的体验与签名一致性有关。本轮没有修改钥匙串或签名策略。

为避免隔离机器出现交互式授权，macOS 验收使用 Electron 的 `--use-mock-keychain`，验证的是测试密钥的跨版本保留，不覆盖真实登录钥匙串的授权提示。不能据此承诺正式用户更新时不会再次看到系统授权框。
