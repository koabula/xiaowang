# 04. Realtime 适配备忘、技术栈倾向与演进路线

后台通用 LLM 的接口如今已高度趋同，兼容各类主流商业模型（Claude、GPT、DeepSeek、Qwen、Gemini 等）及本地模型只需一层极薄的标准 Provider 封装。

真正的工程差异化集中在**前台 Realtime 模型**——各家在连接鉴权、音频帧格式、采样率、打断回执以及异步工具语义上存在显著差异，因此**必须设计一层独立的 Realtime 适配层（Adapter + Local Relay）**，向上暴露统一的语音/多模态会话抽象，向下屏蔽各厂商协议细节。

---

## 一、 首批兼容 Realtime 模型的关键协议备忘

我们先聚焦打通极具代表性的两套模型，它们恰好覆盖了当前业界最主流的两种协议范式：

### 1. `OpenMOSS / MOSS-Live`（原生全双工异步双层范式）
- **为何必须经过本地/服务端中继（Relay）**：WebSocket 握手强制要求在请求头携带 `Authorization: Bearer <KEY>`（纯浏览器端原生 WS 无法注入自定义握手头），且上游对 `session.update` 的字段白名单校验极严（多传未知字段如音色 ID 会直接触发错误断连），适合在中继层统一做密钥托管与字段清洗。
- **媒体流特征**：支持单条连接通过二进制前缀复用上行 16kHz 单声道 PCM 音频（说话停顿期间仍需持续发送静音帧以供模型判断轮次）与视觉画面帧（摄像头/屏幕共享）；下行音频为 **48kHz** PCM。
- **关键机制——播放进度真实回执**：服务端下发音频块的速度远快于实时播放速度（突发下发）。客户端必须以**扬声器真实播放完成**为准逐块发送确认回执；当用户插话触发打断（`response.audio.stop`）时，需立即清空本地未播队列并上报当前块实际已播毫秒数（`played_audio_ms`），从而确保模型准确知道“用户究竟听到了哪半句话”。
- **异步工具优势**：支持异步工具与旁白追加机制（超长任务完成后可追加评论内容，由模型自行寻找对话气口说出）；注意模型默认等待用户先开口，接通时的首句问候适合由客户端本地独立音轨实现。

### 2. `Qwen3.5-Omni-Plus-Realtime`（类 OpenAI 标准 JSON 事件流范式）
- **协议亲和度高**：采用与 OpenAI Realtime 高度一致的 JSON 事件流（`session.update`、`input_audio_buffer.append`、`response.audio.delta` 等），支持多语种语音、可控音色、图像/视频帧输入以及智能语义打断。音频通常为 16kHz 上行、**24kHz** 下行（Base64 封装）。
- **工具调用需异步桥接**：原生 Function Calling 在发出参数事件后默认等待客户端回传 `function_call_output` 与 `response.create` 才会继续说话。接入时直接套用我们协同层的 **「立即回执 + 异步择机注入」** 模式，即可将其丝滑转化为不中断对话的后台任务体验。
- **成本与连接意识**：多模态音频流按 Token 计费成本显著高于纯文本，且接口与地域（如北京 / 新加坡节点）绑定；在客户端设计上有必要考虑**静默空闲自动休眠与开口快速续接**。

### 3. 向更多主流模型的自然延伸
一旦上述两套适配器跑通，后续横向兼容将非常顺滑：
- **OpenAI Realtime / 豆包实时语音（Seeduplex）等**：同属 JSON 事件流 + `call_id` 工具配对体系，可直接复用 Qwen 适配器的绝大部分状态机与音频重采样管线（仅需按需补充如 OpenAI 打断时的 `truncate` 截断事件或 WebRTC 传输选项）。
- **Gemini Multimodal Live 等**：首包 `setup` 配置 + 原生非阻塞工具调用（`NON_BLOCKING`），映射到统一适配接口同样水到渠成。

## 二、 技术栈方向建议（TypeScript 全栈桌面端）

为了最大化开发效率、降低跨语言进程通信心智负担，并获得最稳定的桌面端全双工音视频能力，推荐以 **TypeScript 全栈同构** 作为主技术路线：

- **桌面容器倾向：`Electron`（配合现代构建工具链）**
  - *考量理由*：全双工语音极度依赖稳定的 `AudioWorklet` 重采样、成熟的回声消除（AEC，防止外放声音被麦克风拾取造成自激打断）以及跨窗口论文屏幕捕捉；同时后端需要完整的 Node.js 运行时来承载 WebSocket 中继、官方/社区 TS SDK（如 `@mossai/mosslive`）与本地 MCP 工具子进程。Electron 统一了 Chromium 媒体栈与 Node 进程模型，能避开系统原生 WebView 在音视频权限和编解码上的碎片化问题。
  - *进程解耦建议*：UI 渲染层专注交互流畅度；将 Agent 核心运行时、本地数据存储与 Realtime WebSocket 中继放在独立的后台 Node 进程（或本地守护服务）中运行。甚至可以让核心 `agent-runtime` 保持零 UI 依赖，既能挂在桌面端里跑，也能单独在命令行下做自动化调试与评测。
- **前端工作台：`React` + 轻量状态管理**
  - 聚焦清晰的侧边栏多 Bot 切换、高可读性的科研 Markdown / 公式 / 附件卡片渲染，以及克制的实时语音状态反馈。
- **本地持久化：嵌入式关系库（如 `SQLite`）+ 真实文件系统**
  - 会话事件流、Bot 配置与任务状态适合存入单文件嵌入式数据库（零配置、易备份、读写快）。笔记和脚本放在每个 Bot 自己的工作区；论文等原件放进共享资料库，Bot 只持有引用。用户可以用外部编辑器或 Zotero 直接打开这些真实文件。
- **工具与外部应用生态：应用内能力 + `MCP`**
  - 文件、文献检索、建立新 Bot、快捷搜索，以及应用内浏览器，是小王自己的双手。浏览器嵌在桌面应用里，由小王和用户一起操作，不先依赖一个单独启动的外部浏览器。Zotero、日历、笔记等外部服务可以再走 MCP，避免每个服务都自己写一套协议。

*(注：以上选型为推荐起跑线。若实现阶段在特定模块发现更契合的方案——例如特定音频处理模块、ORM/Schema 工具或跨端形态扩展——完全可以局部替换，只要守住核心模块间的契约边界即可。)*

## 三、 渐进式演进路线（Suggested Milestones）

下面只说明建议顺序。若某一步已经能把一个真实课题做完，可以提前做后面更需要的那一块。每一段都应当单独能用。

1. **阶段一：无头内核与多 Bot 会话基座**（已落地）
   - 已有：Bot 空间隔离、只追加的会话记录、后台工具循环、建立新 Bot、工作区读写、arXiv 作为第一家文献源、命令行入口。模型密钥走环境变量。上下文是投影，记录本身不删。
2. **阶段二：能把文献真正找全的双手**（已落地）
   - 已有：资料库按内容只存一份，Bot 只持有引用；`search_literature` 覆盖 OpenAlex、arXiv、Crossref、PubMed；当前 Bot 能读自己引用的 PDF；快捷搜索在配置 Brave 或 SearxNG 后可用。仍在命令行里。窗口不够时只改投影，会话记录不删。
3. **阶段三：桌面工作台与应用内浏览器**
   - 类 Grok Bot 的多 Bot 导航、对话与产物卡片。设置里填写模型与搜索密钥，存入系统凭据层。应用内嵌一块共用的浏览器面板：你和小王看同一页，可以点击和下载，下载进入资料库并挂到当前 Bot。需要跑代码时，再加工作区沙盒，以及用户按 Bot 授权的外部目录。
4. **阶段四：接入 `MOSS-Live` 与 `Qwen3.5-Omni`，打通统一连续身份**
   - 全双工采集、播放回执与 Realtime 适配。接通前注入当前 Bot 的上下文，通话中把重活派给后台且不打断对话，挂断后文字接着聊。
5. **阶段五：视觉共读、成本与更多实时模型**
   - 屏幕或论文窗口的画面、课题热词、长连接空闲休眠，以及 OpenAI Realtime、Gemini Live、豆包等更多实时模型。
