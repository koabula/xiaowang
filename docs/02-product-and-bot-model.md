# 02. 产品形态与多 Bot 空间模型

「小王同学」采用**桌面客户端**形态，整体交互心智参考 Grok Bot 的多项目空间方案：简洁克制，把复杂的多模态协同隐藏在自然的对话流背后。

---

## 一、 一项目一 Bot：隔离与秩序

在长期的科研与日常使用中，把所有话题塞进同一个超级对话框必然会导致上下文互相污染（比如上午聊生活穿搭和早报，下午审稿讨论特定算法边界）。因此，系统以 **Bot（独立项目/职能空间）** 作为一等公民：

1. **相互独立的专职空间**
   - 左侧导航栏展示不同的 Bot，每一个代表一个长期演进的科研课题（如某个论文选题、某个实验方向）或一项日常职能（如每日早报、资讯分析、生活内务）。
   - **独立边界**：每个 Bot 拥有各自独立的会话历史、课题基线、高频专业术语，以及自己的工作区。工作区用来放这个课题写出来的笔记、脚本和导出物。
   - **问答发生在当前 Bot**：用户切到哪个 Bot，就由那个 Bot 接着自己的会话回答。Bot 之间默认读不到对方的对话和笔记。
   - **并发不串台**：当科研 Bot A 正在检索或下载论文时，用户可以切到日常 Bot B 聊天或开启语音通话，互不阻塞。同一块应用内浏览器同时只有一个 Bot 在操作。

2. **总入口是一个空间，不是调度台**
   - 常驻的「小王同学」是第一个 Bot。还没有单独立项的问答留在这里。它负责在用户要求下建立项目、列出和切换，不代替其他 Bot 回答专项问题。
   - 用户也可以自己手动建立 Bot。任何一个已有 Bot，都可以在用户授意下再建立一个。
   - **典型场景**：在一次宽泛的讨论里发现某个子方向值得深挖，用户说*“把抗改写归因这个方向单独拉个项目跟进，把刚才聊的几篇论文基线同步过去”*。当前 Bot 建立新空间，写入点名的基线，不复制整段对话，并可选地让新项目自己开始第一轮工作。

3. **全局「连接应用」受控共享**
   - 用户的外部工具与账号（如 Zotero、WebDAV 存储、日历、笔记软件）在客户端全局层面统一授权连接一次。模型与搜索服务的密钥在设置里填写，进入系统保护的凭据层。
   - 各个 Bot 无需让用户重复填写登录凭据，即可在允许的权限范围内复用已绑定的能力（例如把核验完的文献写入用户的 Zotero 库）。

## 二、 原件进资料库，笔记留在课题里

用户上传的论文、数据包，以及从小王浏览器下载的文件，往往会被不止一个课题用到。原件放进一份共享资料库，只存一份；每个 Bot 持有自己的引用。

- 上传或下载发生在当前 Bot：文件进入资料库，同时给当前 Bot 一张引用。
- 另一个 Bot 要用，等用户说明，再给一张引用，不复制文件。
- 没有引用的 Bot 读不到这份原件。删掉一个 Bot 时，只要还有别的引用，原件就留着。
- 对照笔记、结论和脚本继续写在各自的工作区里。结论属于课题，不属于那份 PDF。

去重的具体方式、目录怎么摆，实现时可以改，只要用户不用为同一篇论文存很多份，而且课题之间不会自动串稿。

## 三、 应用内的一块浏览器

查「有哪些链接」用快捷搜索，不必开窗口。要点进去、要登录、要下载时，使用嵌在应用里的浏览器面板。不另开一个外部浏览器程序。

这块面板所有 Bot 共用一份登录状态：校园网、知网、Scholar 在这里登录一次即可。你和小王看的是同一块页面，你可以直接点，小王也可以在这上面打开、点击、输入、滚动和下载。密码只在页面里输入，不进对话。遇到登录或验证码，小王把操作交还给你，等你完成后再看页面现在的样子。

下载走浏览器自己的下载。文件进入资料库，并挂到当时正在操作的那个 Bot。付款、提交表单、删除账号数据这类不可逆动作，先停下来等你确认。

同一时刻只有当前 Bot 驾驶这块面板。读到的正文进它的会话，不自动流进其他 Bot。

## 四、 统一连续身份：文本与实时通话的一体化体验

在任何一个 Bot 空间内，用户面对的始终是**同一个「小王」**，只是可以根据当下状态自由切换交互方式：

### 1. 底部对话栏（直接文本与富媒体交互）
- 用户输入文字、拖入论文 PDF / 数据包，直接与后台 LLM 进行深度交互。
- 消息流原生支持结构化 Markdown、文献对照、可下载的本地产物卡片（如整理好的 `.zip` 归档包）。
- 可搭配轻量级的“语音转文字听写”按钮，方便快速口述后手动微调专业缩写再发送。

### 2. 实时全双工通话（Realtime 语音/视觉交互）
- 点击对话栏旁的**通话按钮**，即刻与当前 Bot 建立全双工实时语音连接（后续可叠加屏幕/窗口画面共享，方便看着论文 PDF 聊图表和公式）。
- 支持边听边说、随时插话、自然打断，无需按键等待回合。

### 3. 跨越模态切换的「连续感」要求
对用户而言，以下三个衔接点必须做到无痕过渡：
- **先打字，再打电话**：接通电话时，Realtime 模型已经知晓当前项目的背景以及刚刚在文字框里讨论到的最新进展，用户可以直接接着聊*“刚才你提到的第二点边界问题，我们语音细聊一下”*。
- **边打电话，边出成果**：通话过程中遇到需要查文献、跑脚本、写笔记或整理压缩包的复杂需求，语音对话无需挂起干等；后台 LLM 完成后，详细图文/文件直接落在当前对话框里，口头则在不打断用户说话的前提下择机汇报关键结论。
- **挂断电话，继续打字**：通话期间讨论出的新想法、派发的任务及结论都会沉淀回当前会话。挂断后用户在输入框继续打字追问时，后台 LLM 对刚才电话里聊过的内容了如指掌。

## 五、 留给实现阶段打磨的交互弹性

以下细节不在现阶段做死板规定，可在原型体验中持续调优：
- **通话态的视觉呈现**：通话记录是以逐句气泡实时展开在主对话流中，还是以紧凑的“通话摘要卡片 + 可展开逐字稿”呈现，取决于哪种视觉噪音更小。
- **跨 Bot 知识引用**：默认强隔离。用户若要让课题 B 参考课题 A 的某份笔记，或共用资料库里的某一篇论文，用显式的引用打通。
- **浏览器面板的位置与标签**：可以是对话旁边的一栏，也可以是需要时展开的一块区域。标签如何与 Bot 对应、下载完成时如何同时出现在面板和对话里，看哪种更像一个人在用浏览器。
- **设置页的范围**：模型、搜索服务的地址与密钥放在设置里。还要接哪些外部应用，等真有使用场景再加，不必先做满。
